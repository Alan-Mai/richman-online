## 待驗證假設

### H1：`*.mkf` 與仙劍的 MKF 封包相同，內部資料可能以 YJ1 壓縮
- 依據：同為大宇（Softstar）作品；原版目錄有 `Data.mkf`、`map.mkf`、`Panel.mkf`、`Effect.mkf` 等檔案。
- 狀態：**不成立**。偏移表部分有檔頭反證；壓縮部分也不是 YJ1（本機副本中 462 個壓縮子檔都沒有 `YJ_` magic，實際演算法見「MKF 壓縮」）。
- 可驗證的預測（例）：檔頭是一串 uint32 偏移表，第一個值 ÷ 4 = 子檔數 + 1，最後一個值 = 檔案大小。
- 反證（依 inventory 的 16 bytes 檔頭）：
  - 7 個 `*.mkf` 的第一個 uint32 都接近檔案大小（差 284–5496 bytes），不是小的偏移表長度；其中 5 個甚至不能被 4 整除。
- YJ1 壓縮：
  - 支持：`Data.mkf`、`Panel.mkf` 的第一個子檔看似「原始大小 > 儲存大小」，表示有某種壓縮。
  - 反對（弱）：仙劍的 YJ1 把大小欄位放在 `YJ_1` magic 之後，這裡大小欄位在容器層（見「MKF 容器」）。`help.mkf` 全檔沒有 `YJ_1`，但它也沒有壓縮子檔；壓縮演算法需在 `Data.mkf`、`Panel.mkf` 等檢查。

### H2：`*.mkf` 的索引表在檔尾，每個子檔前有 12 bytes 子檔頭
- 依據（inventory）：
  - offset 0 的 uint32（下稱 `tailOff`）接近檔案大小；7 個檔案的 `size − tailOff` 全部可被 4 整除，像 uint32 表。換算項數：Data 602、Effect 115、Panel 113、Speaking 1374、help 100、jump 71、map 298。
  - offset 4、8 的兩個 uint32 看似第一個子檔的「原始大小」與「儲存大小」：5 個檔案兩者相等（未壓縮），`Data.mkf`、`Panel.mkf` 不等（壓縮）。
  - offset 12 的 uint32 意義不明（觀察值 0、4、16、84、156、528）。
- 狀態：**以 16 bytes 子檔頭修正後成立**，結果整理為「已知格式」的「MKF 容器」條目。
- 可驗證的預測與結果（`help.mkf`，`jump.mkf` 交叉確認）：
  1. 檔尾表（`tailOff` 到檔尾）的值單調遞增。→ 通過。
  2. 檔尾表的值都落在 `[4, tailOff]`；第一個值為 4，最後一個值為 `tailOff`。→ 部分通過：表中存的是各子檔**起點**，最後一個值是最後一個子檔的起點，該子檔結束於 `tailOff`。
  3. 相鄰兩個偏移之差 = 12 + 該子檔的儲存大小。→ 不通過，每項固定多 4；改為 16 + 儲存大小後全部吻合。
  4. offset 4–15 屬於第一個子檔、而非全域檔頭。→ 通過。

### H3：`unknown4 = 512` 的壓縮子檔是壓縮過的 `SPR`，解壓後含 512 bytes 調色盤
- 依據：
  - 未壓縮的 `unknown4 = 512` 子檔開頭為 `SPR\0`，偏移 4、8 的 uint32 形式與 `SMP` 相同（張數 N、`dataOffset` = 12 + 12×N = MKF `unknown3`）。
  - `jump.mkf` 子檔 9–44 的儲存內容前 4 bytes 完全相同，第 6 個 byte 隨 `unknown3` 變化，符合「同一套壓縮處理開頭相同的檔頭」。
  - 512 = 256 × 2：未壓縮 `SPR` 已確認在張數表之後有 256 色 RGB555 調色盤（見「SPR 精靈圖集」）。
- 已知明文與結構限制（用於壓縮分析；依未壓縮 `SPR` 的完整結構）：
  - 前 12 bytes 完全已知：`SPR\0`、N = (`unknown3` − 12) / 12、`unknown3`。
  - 接著 N 筆 12 bytes 張數表：每筆 offset 8 的 uint32 = 寬 × 高，且 N 筆加總 = `rawSize` − `unknown3` − 512。
  - `unknown3` 起 512 bytes 調色盤：每個 uint16 的 bit 15 = 0（即每個奇數位置 byte < 0x80）；未壓縮者 539/549 的第 0 色為 `0x0000`。
  - 之後是 8-bit 索引像素，各張四角多為索引 0（透明色）。
- 可驗證的預測：任一候選演算法把 `jump.mkf` 子檔 9–44 解壓後，長度 = `rawSize`，且能被 `readSpr` 嚴格解析通過。
- 狀態：**成立**。以「MKF 壓縮」解壓後，36 個全部長度 = `rawSize` 且 `readSpr` 嚴格解析通過，`dataOffset` = MKF `unknown3`；縮圖總表經使用者目視確認正確。
- 分析過程（供日後類似工作參考）：
  - 儲存內容的熵約 7.98，明文 `SPR` 不以位元組對齊出現，排除旗標 byte 型 LZSS，改看 bit 串流。
  - 隨 N 變化的 bit 顯示「每個 byte 由最低位元開始讀、碼字由高位元往低位元組合」，且相鄰符號 2k、2k+1 只差最後一個 bit，像依序配對建成的 Huffman 樹；由前幾個字面值的碼字反推出符號數 321。
  - 字面值與長度部分可解出開頭 12 bytes 與張數表前 2 筆，但位置碼在 3 輪、共 132 組參數內未能確定，依時限改用 Ghidra。

## 已知格式

### MKF 容器（`*.mkf`）
- 相關檔案：`Data.mkf`、`Effect.mkf`、`Panel.mkf`、`Speaking.mkf`、`help.mkf`、`jump.mkf`、`map.mkf`
- 推測用途：素材封包，每個子檔是一筆素材。
- 位元組序：little-endian
- 檔頭：
  | offset | 長度 | 型別 | 說明 |
  |---|---|---|---|
  | 0 | 4 | uint32 | `tableOffset`：索引表位置 |
- 主體結構：
  - 子檔從 offset 4 開始連續排列，每個子檔 = 16 bytes 子檔頭 + `storedSize` bytes 內容。
  - 子檔頭：
    | offset | 長度 | 型別 | 說明 |
    |---|---|---|---|
    | 0 | 4 | uint32 | `rawSize`：推測為解壓後大小 |
    | 4 | 4 | uint32 | `storedSize`：檔內實際儲存的內容長度 |
    | 8 | 4 | uint32 | `unknown3`：意義未知 |
    | 12 | 4 | uint32 | `unknown4`：意義未知 |
  - `[tableOffset, EOF)` 是 N 個 uint32 的子檔起點，N = (檔案大小 − `tableOffset`) / 4；起點嚴格遞增，第一個為 4。
  - 每個子檔結束於下一個子檔的起點，最後一個結束於 `tableOffset`。允許 `storedSize` = 0 的空子檔。
- 壓縮/加密：容器本身無。`rawSize` ≠ `storedSize` 的子檔以「MKF 壓縮」儲存，`rawSize` 是解壓後大小（462 個全部吻合）。
- 調色盤來源：不適用。
- 證據：
  - `help.mkf` 驗證 H2 的四個預測，並由此修正子檔頭為 16 bytes。
  - 嚴格解析器與逐項檢查（不在第一個錯誤停下）跑完 7 個檔案，都沒有例外：
    | 檔案 | 子檔數 | raw = stored | raw > stored | 空子檔 |
    |---|---|---|---|---|
    | `Data.mkf` | 602 | 291 | 311 | 0 |
    | `Effect.mkf` | 115 | 115 | 0 | 16 |
    | `Panel.mkf` | 113 | 21 | 92 | 0 |
    | `Speaking.mkf` | 1374 | 1374 | 0 | 0 |
    | `help.mkf` | 100 | 100 | 0 | 0 |
    | `jump.mkf` | 71 | 35 | 36 | 0 |
    | `map.mkf` | 298 | 275 | 23 | 0 |
  - 沒有任何子檔 `rawSize` < `storedSize`。
- 解析器：`tools/extract/src/formats/mkf.ts`（只讀索引表與子檔頭，內容以 offset 按需讀取）
- `unknown3`、`unknown4` 的觀察（名稱維持中性）：
  - 「`unknown3 + unknown4 = rawSize`」**並非所有子檔都成立**。7 個檔案的子檔分成三類，沒有例外：
    | 檔案 | `u3 + u4 = rawSize` | (0, 0) | `u4 = 512`（其中壓縮） |
    |---|---|---|---|
    | `Data.mkf` | 240 | 72 | 290（2） |
    | `Effect.mkf` | 16 | 99 | 0 |
    | `Panel.mkf` | 35 | 12 | 66（64） |
    | `Speaking.mkf` | 0 | 1374 | 0 |
    | `help.mkf` | 1 | 99 | 0 |
    | `jump.mkf` | 10 | 25 | 36（36） |
    | `map.mkf` | 21 | 8 | 269（2） |
  - `map.mkf` 的分類（盤點更正）：`u3 + u4 = rawSize` 的 21 個**全部是壓縮子檔**（16–24、27–38），加上 `u4 = 512` 中的 2 個壓縮子檔（25、26），正好是它的 23 個壓縮子檔；(0, 0) 的 8 個**正是地圖資料**（奇數子檔 1–15，見「地圖資料」）。
  - `SMP` 子檔（17 個）：`unknown3` = `SMP` 的 `dataOffset`（檔頭 + 張數表長度），`unknown4` = 像素資料長度，全部吻合。
  - `unknown4 = 512` 的子檔：未壓縮者開頭為 `SPR\0`（549 個）或 `GND\0`（`map.mkf` 8 個），共 557 個。`SPR` 已確認：`unknown3` = `SPR` 的 `dataOffset`，`unknown4` = 調色盤長度 512（549 個全部吻合，見「SPR 精靈圖集」）。`GND` 已確認：`unknown3` = 16 = 調色盤位置，`unknown4` = 調色盤長度 512（8 個全部吻合，見「GND 地圖背景」）。`jump.mkf` 的 36 個壓縮子檔就是它的 36 個 `unknown4 = 512` 子檔。
  - 全螢幕圖（`rawSize` = 614400，共 9 個）：`unknown3` = 4、`unknown4` = 614396，仍滿足相加等於 `rawSize`，但**內容沒有 4 bytes 檔頭**，像素從 offset 0 開始。比較兩種解讀（`jump.mkf` 子檔 0–7）：
    - 前 4 bytes：子檔 1、4 的前兩個 uint16 與第 3 個像素相同（整片同色區域），像正常像素而非檔頭欄位；其餘子檔的值也沒有一致的檔頭特徵。
    - 若像素從 offset 4 開始，從 offset 0 讀時每列會在第 1→2 欄之間出現接縫，且第 y 列右緣應與第 y+1 列左緣連續。實測第 1→2 欄的平均顏色差與第 2→3 欄相近（例：0.64 對 0.83），而右緣→下一列左緣的差一般較大（例：3.12、10.40），支持 offset 0。子檔 1、7 畫面較平坦，三個值接近，不具鑑別力。
    - 從 offset 4 讀只剩 307198 個像素（少 2 個），無法組成完整的 640×480。
    - 結論：全螢幕圖的 `unknown3` 不是內容內的檔頭長度；其意義未知。
- 待解問題：
  - `unknown3`、`unknown4` 在全螢幕圖與 (0, 0) 類中的意義（`SMP`、`SPR`、`GND` 已確認；`map.mkf` 的 (0, 0) 類是地圖資料，兩欄都為 0）。
  - 讀檔後處理（見「MKF 壓縮」的待解問題）。

### MKF 壓縮（LZ + 動態 Huffman）
- 相關檔案：`rawSize` ≠ `storedSize` 的 MKF 子檔，本機副本中共 462 個（`Data.mkf` 311、`Panel.mkf` 92、`jump.mkf` 36、`map.mkf` 23）。
- 用途：子檔內容的無損壓縮。壓縮資料沒有自己的檔頭或 magic，解壓後大小取自 MKF 子檔頭的 `rawSize`。
- 演算法（屬 LZ77 + 動態 Huffman，與 1988 年公開的 LZHUF 同一家族，以下為與 LZHUF 不同處在內的完整描述）：
  - **bit 讀取**：依序取 byte，每個 byte 從最低位元開始；中途不對齊到 byte 邊界。
  - **符號**：321 個。0–255 為字面值，256–320 為參照，長度 = 符號 − 253（3–67）。
  - **Huffman 樹**：初始時 321 個葉節點頻率都是 1，內部節點依序把相鄰兩個節點配對而成（節點按頻率排序存放）。從根往下每讀一個 bit 走一層，0 走第一個子節點、1 走第二個。初始碼長為 8 或 9 bit。
  - **更新**：每解出一個符號，就把它的葉節點到根的頻率各加 1；某節點加 1 後若大於後面節點的頻率，就和「頻率仍較低的最後一個節點」交換位置，以維持排序。這與 LZHUF 相同。
  - **頻率上限**：更新前若根的頻率剛好等於 0x8000，先把頻率為奇數的符號各多更新一次（讓所有頻率變成偶數），再把所有節點的頻率右移一位減半。樹的形狀不變。LZHUF 在這裡是重建整棵樹，這點不同。
  - **參照位置**：先預看接下來 8 bit（第一個 bit 為最低位），查表得到前綴長度 L（3–8）與位置的高 6 bit；跳過 L bit 後再讀 6 bit 低位（同樣第一個 bit 為最低位）。位置 p = 高 6 bit × 64 + 低 6 bit。
  - **前綴碼規則**：長度 3、4、5、6、7、8 bit 各有 1、3、8、12、24、16 個碼，共 64 個，對應高 6 bit 的 0–63。碼以標準方式依長度遞增配給（高位元在前、逐一加 1，長度增加時左移補位），再把每個碼的 bit 全部反相並反轉順序，得到「第一個 bit 為最低位」的查表鍵。高 6 bit 依長度由短到長配給；同一長度內，較小的值配給較大的鍵。查表在程式中依這條規則產生，與 `rich4.exe` 內的表逐項比對 512 項全部相同（未把表放進倉庫）。
  - **複製**：從目前輸出位置往回 p + 1 bytes 開始，逐 byte 複製長度個 byte，可與正在寫的區域重疊。視窗就是輸出本身，沒有環形緩衝區或預填值。
  - **結束**：p = 4095 是結束標記，與它一起出現的長度符號不使用。
- 證據：
  - 開頭的字面值、長度、Huffman 樹形狀以 `SPR` 已知明文黑箱推得（見 H3 的分析過程）；位置碼、頻率上限的處理、結束標記與「沒有環形緩衝區」由 Ghidra 分析 `rich4.exe` 確認（解壓函式約在 `0x455040`，由讀檔函式 `0x450441` 呼叫）。反編譯輸出只留在本機 `local-assets/`，未進入倉庫。
  - 收集模式跑完 7 個 MKF 的全部 462 個壓縮子檔：都以結束標記結束、輸出長度 = `rawSize`、輸入剛好用完 `storedSize`、沒有參照落在輸出開頭之前，沒有例外。
  - 解壓後依 magic 分開計：`SPR` 104 個（`jump` 36、`Panel` 64、`Data` 2、`map` 2）全部通過 `readSpr` 嚴格解析，`dataOffset` = MKF `unknown3`、`unknown4` = 512；`SMP` 50 個（`map` 21、`Panel` 22、`Data` 7）全部通過 `readSmp` 嚴格解析，`dataOffset` = MKF `unknown3`；沒有已知 magic 的 308 個（`Data` 302、`Panel` 6）尚未分析。
  - `jump.mkf` 子檔 9–44 的縮圖總表經使用者目視確認正確。
- 解析器：`tools/extract/src/formats/mkf-compression.ts`（`decompressMkf`；嚴格：缺結束標記、輸出長度不符、參照越界、結束後仍有剩餘 byte 都報錯）
- 待解問題：
  - **讀檔後處理**：讀檔函式解壓之後，若子檔頭 `unknown4` ≠ 0，會對 `[unknown3, unknown3 + unknown4)` 這段呼叫另一個函式（`0x451801`），尚未分析。推測（低信心）：把調色盤轉成顯示用的像素格式；以 RGB555 直接解讀調色盤的色彩已經正確，所以不影響目前的轉檔。
  - **開頭 3 bytes 比對**：讀檔函式會把輸出的前 3 bytes 與兩個 3 字元常數比對，相符時再呼叫另一個函式（`0x450069`），尚未分析。推測（低信心）：依 `SPR`/`SMP` 等 magic 分派不同的後續處理。
  - 原版的解壓函式不檢查邊界；本解析器維持嚴格。

### SPR 精靈圖集
- 相關檔案：`Data.mkf` 288 個、`Panel.mkf` 2 個、`map.mkf` 259 個（共 549 個，皆未壓縮；MKF `unknown4` = 512）。另有壓縮的 104 個（`jump.mkf` 子檔 9–44 共 36、`Panel.mkf` 64、`Data.mkf` 2、`map.mkf` 2），解壓後結構相同（見「MKF 壓縮」、H3）。
- 推測用途：多張 8-bit 調色盤圖片的集合（角色動作、地圖建物、UI 元件）。
- 位元組序：little-endian
- 檔頭：
  | offset | 長度 | 型別 | 說明 |
  |---|---|---|---|
  | 0 | 4 | char[4] | magic `SPR\0` |
  | 4 | 4 | uint32 | 張數 N |
  | 8 | 4 | uint32 | `dataOffset` = 12 + 12×N（= MKF `unknown3`） |
- 主體結構：
  - offset 12 起為 N 筆 12 bytes 的張數表：
    | offset | 長度 | 型別 | 說明 |
    |---|---|---|---|
    | 0 | 2 | uint16 | 寬 |
    | 2 | 2 | uint16 | 高 |
    | 4 | 2 | int16 | `unknown3`：意義未知（疑似錨點 x，未確認） |
    | 6 | 2 | int16 | `unknown4`：意義未知（疑似錨點 y，未確認） |
    | 8 | 4 | uint32 | 像素長度 = 寬×高 |
  - `dataOffset` 起 512 bytes：256 色調色盤，每色一個 RGB555 uint16。
  - `dataOffset + 512` 起依序存放各張像素，每像素 1 byte 調色盤索引，由上而下、由左而右；各張緊密相接，最後一張結束於資料尾端。

- 調色盤來源：檔內（每個 `SPR` 各自一組）。
- 透明色：調色盤索引 0（不論該色的值）。依據：四角像素 99.5% 為索引 0，10659 張中 10522 張四角全為 0，只有 25 張完全沒用到索引 0；轉 PNG 時把索引 0 畫成洋紅色，經使用者目視確認都落在背景位置。

  - x：其中 13 張變成負數（最小 −68），其餘 15 張仍為正且超出寬，最多超出 49。
  - y：其中 18 張變成負數（最小 −103），其餘 112 張仍為正且超出高，最多超出 58。
  - 全部 10659 張的範圍：x ∈ [−68, 221]、y ∈ [−103, 230]。以 uint16 讀，負數會變成 65000 以上的孤立值，int16 較合理。
  - 若為錨點，代表錨點可以落在圖外；意義仍待對照遊戲畫面確認。
- 證據：
  - 調色盤位置：檔頭與張數表之後的 512 bytes，549 個全部 bit 15 = 0；若改取檔尾 512 bytes，有 542 個出現 bit 15 = 1（是像素資料），排除。
  - 549 個檔案、10659 張，每張大小 = 寬×高，總長 = `dataOffset` + 512 + 各張大小，全部吻合。
  - `Data`、`Panel`、`map` 各取數個轉 PNG（角色走路、計算機面板、旋轉建物），經使用者目視確認色彩與透明位置正確。
  - 嚴格解析器以收集模式跑完 7 個檔案的所有未壓縮子檔：549 個 `SPR` 全部通過，沒有結構例外；MKF `unknown3` 都等於 `dataOffset`，`unknown4` 都等於 512；調色盤 bit 15 都為 0；沒有寬或高為 0 的圖。
- 解析器：`tools/extract/src/formats/spr.ts`
- 待解問題：
  - 張數表的 `unknown3`/`unknown4`（疑似錨點，可落在圖外）需對照遊戲畫面確認。
  - 調色盤第 0 色不是 `0x0000` 的 10 個，都在 `Data.mkf`。第 0 色都是很暗的灰色，但不知為何不是 `0x0000`：

    | 399 | `0x0421` |
    | 400 | `0x0442` |
    | 401 | `0x0421` |
    | 402 | `0x0462` |
    | 403 | `0x0862` |
    | 404 | `0x0420` |
    | 407 | `0x0862` |

### GND 地圖背景
- 相關檔案：`map.mkf` 偶數子檔 0、2、…、14（8 個，皆未壓縮；MKF `unknown3` = 16、`unknown4` = 512）。
- 推測用途：地圖的完整背景圖，每個對應一張地圖；下一個奇數子檔是該地圖的地圖資料（見「地圖資料」，待分析）。
- 位元組序：little-endian
- 檔頭：
  | offset | 長度 | 型別 | 說明 |
  |---|---|---|---|
  | 0 | 4 | char[4] | magic `GND\0` |
  | 4 | 2 | uint16 | 欄數（格子寬） |
  | 6 | 2 | uint16 | 列數（格子高） |
  | 8 | 4 | uint32 | `unknownAt8`：意義未知（本機副本中都等於欄數 × 列數，也等於圖塊數，無法區分） |
  | 12 | 4 | uint32 | `unknownAt12`：意義未知（本機副本中都為 0） |
- 主體結構：
  - offset 16 起 512 bytes：256 色 RGB555 調色盤（= MKF `unknown3` 起、長 `unknown4`，與 `SPR` 相同）。
  - offset 528 起：欄數 × 列數個 uint16，每格使用的圖塊編號，由上而下、由左而右。
  - 之後：圖塊，每塊 32 × 32 個 8-bit 調色盤索引，由上而下、由左而右；圖塊數 = 剩餘長度 ÷ 1024。
  - 整張圖 = (欄數 × 32) × (列數 × 32) 像素。
- 圖塊大小 32 × 32 **不在檔頭**，是推論：剩餘長度剛好是 1024 的整數倍，依此拼出的背景畫面連續；以 72 為圖塊邊長時畫面錯位。
- 壓縮/加密：無。
- 調色盤來源：檔內。
- 透明色：不適用（整張背景）；8 個調色盤的第 0 色都是 `0x0000`。
- 證據：
  - 嚴格解析器以收集模式跑完 7 個檔案的所有未壓縮子檔：8 個 `GND` 全部通過，沒有結構例外；網格都是 72 × 72、圖塊都是 5184 塊；MKF `unknown3`/`unknown4` 都是 16/512；調色盤 bit 15 都為 0。
  - 本機副本中，8 個的圖塊編號表都是 0、1、2、… 依序排列（每格各自一塊，沒有共用）。解析器不假設這點，只檢查編號小於圖塊數。
  - 8 張以縮圖目視檢查，海岸線、道路、地塊外框都連續，沒有接縫或錯位。子檔 0 疊上地圖資料的座標後，各點都落在背景畫出的格子與地塊上。
- 解析器：`tools/extract/src/formats/gnd.ts`（`composeGnd` 拼出整張索引圖）
- 待解問題：
  - `unknownAt8`、`unknownAt12` 的意義。
  - 子檔 8 拼出來幾乎全黑、只有零星色點，與其他 7 張不同；但對應的地圖資料（子檔 9）有完整棋盤。背景上沒有畫出道路，道路可能由其他子檔（例如每張地圖一個的壓縮子檔 16–23）疊加，需對照遊戲畫面確認。

### 地圖資料（`map.mkf` 奇數子檔）
- 相關檔案：`map.mkf` 奇數子檔 1、3、…、15（8 個，皆未壓縮；MKF `unknown3`/`unknown4` 為 (0, 0)；沒有 magic）。子檔 2k+1 是子檔 2k（`GND`）那張地圖的資料。
- 用途：棋盤（格子位置、相鄰關係）、一般地塊（區段 1）、大型建築用地（區段 2）、地點（區段 3）、標籤與圖像（區段 4）。區段用途與下列欄位用途的證據來自 Ghidra 分析 `rich4.exe`（函式位址為本機副本 exe 中的位址；逆向範圍見 `DECISIONS.md`）。
- 載入方式（LoadMap 0x00407ad2）：整個子檔讀進一塊 buffer，不拷貝；每個區段以「buffer + 檔頭偏移」當作第 0 筆的位址，程式一律從第 1 筆用起。這塊 buffer 會整塊寫進存檔（0x00402ac5／0x00402fd1），所以檔案中全為 0 的欄位多是**執行期狀態**（擁有者、等級、上次收取的過路費、租約到期日等），不是填充。
- 位元組序：little-endian
- 檔頭：80 bytes = 20 個 uint32：
  | slot | offset | 說明 |
  |---|---|---|
  | 0 | 0 | n0：區段 0 筆數 |
  | 1 | 4 | 區段 0（格子）的基底偏移：指向虛擬的第 0 筆，剛好等於步長 40（解析器檢查，錯誤碼 `bad-square-base`）。格子沒有佔位紀錄，第 0 筆與檔頭後半重疊，第 1 筆正好在 80 bytes 檔頭之後（原本誤記為「每筆長度」，LoadMap 是把它加到 buffer 起點當基底） |
  | 2、3 | 8、12 | n1、區段 1 起點 |
  | 4、5 | 16、20 | n2、區段 2 起點 |
  | 6、7 | 24、28 | n3、區段 3 起點 |
  | 8、9 | 32、36 | n4、區段 4 起點 |
  | 10–19 | 40–79 | 本機副本中都為 0 |
- 主體結構：
  - 區段 0 從 offset 80 開始，長度 n0 × 40。
  - 區段 1–4 的長度 = (n + 1) × 每筆長度（52、56、52、28）：**第 0 筆是全 0 的佔位紀錄**，之後才是 n 筆資料。檔內參照都是從 1 起算，0 表示「無」，正好跳過佔位紀錄。
  - 五個區段依序緊密相接，區段 4 結束於子檔尾端。
  - 每筆紀錄的共同開頭：
    | offset | 長度 | 型別 | 說明 |
    |---|---|---|---|
    | 0 | 2 | int16 | x（像素，對應 `GND` 背景） |
    | 2 | 2 | int16 | y（像素） |
    | 4 | 10 | char[10] | 名稱，Big5，以 NUL 結尾、補 0 |
  - 區段 0（格子，40 bytes）：
    | offset | 長度 | 型別 | 說明 |
    |---|---|---|---|
    | 14 | 10 | — | 本機副本中都為 0 |
    | 24 | 8 | uint16[4] | 相鄰格子（區段 0 的編號，從 1 起算，0 = 無）；**4 個槽位地位相同**，沒有「下一格／上一格」之分；**無方向**（移動規則只靠玩家的「上一格」，見 `GAME_RULES.md` 第 2 節） |
    | 32 | 2 | uint16 | 參照：1000 × 類別 + 編號；類別 0 = 無、2/4/6/8 = 區段 1/2/3/4。程式以「參照 − 2000／4000／6000／8000」直接得到區段 1–4 的編號，載入時不轉換 |

### `rich4.exe` 資料表
- 相關檔案：`rich4.exe`（PE32）。本機副本的區段名稱不是常見的 `.text`／`.data`：程式碼在 `AUTO`，初始化資料在 `DGROUP`，各區段的 VirtualSize 都是 0（以 raw size 為映射大小）。
- 用途：原版規則與動畫用到的資料表。依 `DECISIONS.md`「執行檔內的資料表由玩家本機匯出」，數值不進倉庫，由 `pnpm -F extract cli tables` 匯出到 `local-assets/tables.json`。
- 定位：寫死本機副本的虛擬位址（`tools/extract/src/exe-tables.ts` 的 `RICH4_LAYOUT`），不用程式碼特徵碼。匯出時逐表檢查，任一項不符就報「unsupported rich4.exe」並指出是哪張表、哪一項，不印數值：
  - PE32 結構（MZ、PE 簽章、PE32 magic）。
  - 整張表落在同一個區段有檔案內容的範圍內。
  - 程式碼區段（依區段屬性判斷）中，至少有一個 4 bytes 絕對位址落在表的範圍內（不要求指向表頭，例如只參照某筆的某欄位）。
  - 規則性質，各有 `GAME_RULES.md` 的依據：每幀位移 > 0（每步幀數以它為除數）；起始資金各檔 > 0（物價指數以它為除數）；天數上限與淨值目標倍數的第 1 檔為 0（「不限」）。
  - 字串表（天數上限的選項文字）：每個指標都落在有檔案內容的區段內，指向 1–64 bytes、以 NUL 結尾的字串，能以 Big5 嚴格解碼（錯誤訊息只說哪一檔、哪一項檢查失敗，不印內容）。
